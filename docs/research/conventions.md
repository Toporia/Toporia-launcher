# Reproduction conventions

## One traceable example per numerical function

Track a function by `kind:name`, not by menu label or a generated pairing. Select
an identifiable paper, figure and panel; record its exact setup before running.
A shared example can cover multiple functions, but a successful overall design
does not validate every internal detail. Match the evidence to each function.
An optimizer may need a convergence curve, a filter a field, a material law a
constitutive curve and a physics engine an independent state benchmark.

## Evidence has separate levels

| Status | Evidence required |
| :-- | :-- |
| Pending | Function and existing citations inventoried; figure still to select. |
| Attempted | Runnable recipe, generated figure and complete settings recorded. |
| Native-code match | Defined numerical tolerances met against an identified independent source. |
| Paper visual match | Identified panel inspected; topology/features agree qualitatively. No pixel/numerical equality implied. |
| Paper numerical match | Explicit published measurements agree within declared tolerances on the same setup. |
| To fix | A required comparison failed, information is missing, or implementation differences prevent an honest match. |

Native agreement and paper comparison are separate fields, not one green tick.
Keep image interpolation, thresholding, field orientation and normalization
explicit. Do not compare a pre-update objective with a fresh final-design solve.
Physical volume, objective, stopping reason, iteration cap and source hashes
belong in every numerical report. Mark altered discretizations and formulations
as variants, even when the pictures resemble each other.

## Tolerances

Declare them before comparing. Batch 1 uses final density max absolute error
1e-7, all printed compliance samples within 5.1e-5 (four-decimal source output),
mean density within 1e-8 and identical iteration counts. These test equivalence
of this implementation and source recipe, not publication-wide accuracy.
MATLAB's top-down image rows are converted once to Toporia's bottom-up physical
coordinates before comparing. This fixed convention is recorded in each report;
no rotation, reflection search or visual best-fit alignment is performed.
Other physics and digitized paper curves need their own justified tolerances.

## Description and math

Declare `DESCRIPTION` alongside the preset using the plain data classes in
`plugins/problems/_research.py`. Include the question, setup, computation,
equations with short explanations, symbols/units, source, target panel,
comparison method, limitations, rerun command and function IDs. No executable
code or HTML goes in description text. Equations use MathText without `$`.
The renderer embeds locally typeset images so Qt can display fractions,
subscripts and matrices without showing LaTeX source. Keep equations short
enough to read in the help panel. Explain implementation math, not only a
paper's abstract formulation.

## Bounded unsuccessful attempts

Keep the recipe and failed evidence; never weaken a tolerance to turn a failure
green. Place unresolved records in `to-fix/<case>/` using the template. Record
the next discriminating check, not an unbounded promise to tune parameters.
Researcher corrections are attributed and tied to the implementation/version
they assess. Existing golden baselines are never regenerated by this workflow.
